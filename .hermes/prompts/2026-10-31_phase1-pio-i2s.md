## Project context

"Zuko (RP2350)" is a standalone digital guitar stompbox on a Raspberry Pi Pico 2 (RP2350A, dual
Cortex-M33, hardware single-precision FPU, ARMv8-M DSP extensions). It will model two British tube
preamps (Marshall 1959 Super Lead "Plexi" and Marshall JCM800 2203), a passive FMV tone stack, a
presence filter and a Marshall 1960B 4x12 cabinet IR via 1024-tap direct-form FIR. The preamp is
modeled **analytically** (tanh triode waveshapers with bias and cathode sag). **There is no neural
network anywhere in this project — do not propose NAM.**

Phase 0 is complete and verified: the skeleton builds inside Docker (`pio run -e rpipico2`), the
hardware FPU is confirmed in the linked ELF (`vfma.f32`/`vmul.f32` present, no `__aeabi_fmul`), and
CMSIS-DSP `arm_fir_f32` links. Read `docs/BUILD-NOTES.md`, `docs/PINOUT.md` and `README.md` before
writing anything.

## Architecture decisions already made — do NOT re-litigate or change them

1. **I2S clocking is route B: the RP2350 generates the entire clock tree; the converters are
   slaves.** `clk_sys` = 245.76 MHz, so every division is an integer: `MCLK` = clk_sys / 20 =
   12.288 MHz, `BCLK` = clk_sys / 40 = 3.072 MHz, `LRCK` = 48 kHz (32-bit slots per channel).
   Route A (an external 12.288 MHz oscillator, PIO in slave mode) was explicitly rejected — do not
   switch to it, and do not switch the PIO to slave mode.
2. Audio format is I2S, 24-bit data in 32-bit slots, MSB-first, standard one-bit clock delay
   relative to LRCK.
3. Core 0 does audio only. Core 1 owns UI, control and coefficient calculation (idle in this phase).
4. **Never enable the RP2350 internal pull-DOWN resistors** (documented silicon erratum: the pin
   latches low after the first read). Internal pull-UP or external resistors only.
5. Block size is **32 samples per channel**.
6. Toolchain: PlatformIO, platform `maxgerhardt/platform-raspberrypi`, framework `arduino`,
   `board_build.core = earlephilhower`, board `rpipico2`, `-O3` + `-DARM_MATH_CM33` +
   `-D__FPU_PRESENT=1U` + `-fsingle-precision-constant`. Do not add `-ffast-math`.

## Pin map — authoritative, use exactly this

| Function | GPIO | Notes |
|---|---|---|
| I2S MCLK **output** (to PCM1808 SCK) | GP19 | 12.288 MHz = clk_sys / 20 |
| I2S BCLK **output** (to PCM1808 BCK and DAC BCK) | GP21 | 3.072 MHz; must be adjacent to GP22 |
| I2S LRCK **output** (to PCM1808 LRCK and DAC LRCK) | GP22 | 48 kHz |
| I2S DIN **input** (from PCM1808 DOUT) | GP20 | any pin works |
| I2S DOUT **output** (to PCM5102A DIN) | GP23 | any pin works |
| Status LED | GP15 | already used by the Phase 0 blink — keep it blinking |

GP21/GP22 must be driven as an **adjacent pair** (a 2-bit side-set always addresses two neighbouring
pins). GP20 and GP23 are free pins.

## Requirements — the driver

- **PIO in master mode.** Two implementations are acceptable and both fit this pinout; pick one and
  justify it in `docs/I2S.md`:
  1. one state machine in full duplex (`out pins, 1` for DOUT, `in pins, 1` for DIN, side-set for
     BCLK/LRCK) — fewest resources; or
  2. two state machines: an output master generating BCLK/LRCK by side-set, plus an input machine
     waiting on those same pins — the configuration the community reference
     (`https://github.com/malacalypse/rp2040_i2s_example`) recommends as more robust.
- **MCLK on GP19.** Use the cheapest correct mechanism that produces an exact 12.288 MHz
  (`clock_gpio_init` from the SDK is preferred over spending a PIO state machine on it, if that
  helper exists in this framework — verify, and say which you used).
- **DMA ping-pong over 32-sample blocks.** State explicitly in your report **how many DMA channels
  you used and why**. If a correct full-duplex ping-pong needs more than two channels, say so
  plainly instead of bending the design to fit an expected number.
- Buffer the audio in SRAM, and put the block handler in `__not_in_flash_func`. The correct syntax
  is `return_type __not_in_flash_func(function_name)(args)` — never
  `__not_in_flash_func(return_type function_name)(args)`.
- **Pass-through only**: copy the 32 received samples to the 32 transmitted samples for both
  channels, with no gain, no filtering and no processing. The point of this phase is that audio
  survives the round trip.
- Handle underruns/overruns without hanging: never block the audio path on Serial output.

## Requirements — the CPU budget (this is an acceptance criterion, read carefully)

The design must declare a **measured** block-processing budget rather than a guess. Since no hardware
exists yet, "measured" means: **the firmware contains the instrumentation that measures it, and the
method is documented and runnable.** You must NOT claim a measured number.

- Instrument the block handler with the core cycle counter (whatever this framework/SDK actually
  exposes — verify the API in the sources; if you are not certain it exists, say so and use an
  alternative you can verify). Accumulate min / average / max cycles per block and report over
  Serial every N blocks (N ~ 100), together with the implied percentage of the core.
- The reference numbers, computed for you (do not re-derive them wrong):
  - 32 samples/channel × 2 channels × 32 bits = **2048 bit-clocks per block**
  - 2048 / 3.072 MHz = **666.7 µs per block**
  - at 245.76 MHz that is **163,840 CPU cycles of wall-clock budget per block**
  - one block of latency = 0.667 ms; worst-case double buffering = 1.333 ms (the roadmap asks for
    < 2 ms, so this fits — but say so with the numbers, not as a feeling)
- `docs/I2S.md` must contain: the budget table above, the measured-on-hardware procedure, and the
  decision rule (for example: if the pass-through handler exceeds X cycles per block, the DSP chain
  will not fit and the block size or the platform must be revisited).
- State clearly which numbers are **computed** and which are **not yet measured**.
